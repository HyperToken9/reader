# 11 — Can a local neural TTS model replace the browser's voices, and what timing does it give back?

Type: research
Status: resolved
Blocked by: —

## Question

[[10]] dropped the word cursor and deferred voice quality, and both of those decisions rest on the same premise: **that TTS means the Web Speech API**. On Linux that API delivers no word-boundary events for any voice, and only speech-dispatcher's local voices, which are robotic. A locally-executed neural model breaks that premise from both ends at once — better voices *and* its own timing data — so this is worth establishing before [[05]]'s voice verdict is treated as final.

Named by the human: **Kokoro** (Kokoro-82M, ~82M params, Apache-2.0, claimed to run on CPU, ONNX builds exist) and "**omnitts**", which I can't place with confidence — find out what they meant, or what the nearest real thing is. Other candidates worth pricing at the same time: **Piper** (fast, small, phoneme-timed, built for exactly this), **MeloTTS**, **F5-TTS**, **XTTS-v2**, **Chatterbox**, and whatever has landed since. This area moves fast; prefer current model cards and repos over recollection.

For each serious candidate, establish:

- **Does it return alignment data**, and at what granularity — word, phoneme, or nothing? This is the load-bearing question, because it is the only thing that would reopen the word cursor [[10]] dropped. Piper emits phoneme timings; Kokoro goes through a phonemiser (misaki) that may or may not surface them. Note whether alignment comes free with synthesis or needs a separate forced-alignment pass.
- **Latency to first audio**, on CPU, on this machine, for one sentence. Reading aloud must start when you press play, not after a model warms up. Establish both cold-start and steady-state, and whether synthesis can be pipelined a sentence or two ahead the way [[04]] has utterances queued now.
- **Real-time factor** — can it synthesise faster than it speaks, on CPU alone? If it needs a GPU, say what happens without one.
- **How it is actually invoked from an app.** Python process? ONNX Runtime via `onnxruntime-node`? WASM in the browser? This is the fact that matters most to [[08]], because "needs a Python sidecar" and "runs in a tab" are different products.
- **Voice quality and voice choice**, honestly assessed. Sustained textbook reading is hours, not a demo sentence.
- **Licence and model weight size**, since these ship with the app.

Also answer the design question that falls out: if audio arrives as a buffer rather than through `speechSynthesis`, the band no longer moves on `onstart`/`onend` — it moves off the audio element's clock plus the alignment data. **That re-introduces the timing seam [[04]] proposed and [[10]] cancelled.** Say plainly whether it comes back, and in what shape.

Do not decide whether to adopt this; establish what is true. The decision is a later ticket, and it depends on [[05]]'s verdict on whether the cheap thing was already good enough.

## Answer

Full findings, with every measurement and its script: [research/11-local-neural-tts.md](../research/11-local-neural-tts.md). Both candidates were **installed and run on this machine** — `pip install piper-tts` and `pip install kokoro-onnx`, `onnxruntime` 1.23.2 straight from PyPI, no compiler, no CUDA, no system packages. "Needs a model runtime" cost two pip installs. Everything below is measured here on CPU unless flagged otherwise.

**Yes, they return alignment data, and Piper's is exact.** This is the load-bearing answer and it is stronger than the ticket hoped for. Piper 1.8.0 returns a per-phoneme **sample count** for every phoneme it synthesised (`AudioChunk.phoneme_alignments`, an alignments feature added in v1.3.1 and documented in `docs/ALIGNMENTS.md`). I checked whether those counts account for the audio: on three sentences the sum of alignment samples equalled the produced audio **exactly — zero sample error**. That is structural, not luck. Piper is a VITS model; the duration predictor decides how many frames each phoneme gets and the vocoder produces exactly that. The alignment is a *partition* of the waveform, not a measurement of it, so there is no calibration constant, no accumulating error, and **nothing that can drift**. It costs ~1.6% synthesis overhead. The one setup wrinkle: the voice must be "patched" (`include_alignments=True` at load, which is most of the 929 ms load cost, or pre-patched once via CLI) and that needs the `onnx` package alongside `onnxruntime`.

**Kokoro has timings too, but they are a second-class path.** The plain `kokoro-v1.0.onnx` outputs audio only — read straight off the graph, its sole output is `audio`. Phoneme timings require the separate community re-export `onnx-community/Kokoro-82M-v1.0-ONNX-timestamped` (Apache-2.0, fp16 163 MB), whose graph adds a `durations` output. `kokoro-onnx` has a `create_timed()` API for exactly this and it **silently returned nothing**: `Kokoro._setup` checks for an output named `"duration"` while the export names it `"durations"`, so `has_timings` stays `False` with no error. Forcing it true produced correct `Timing(phoneme, start, end)` objects immediately. A one-line upstream bug, but a fair maturity signal — Piper's alignment is a tested feature, Kokoro's is a community export plus a library that can't detect it. (The PyTorch `kokoro` package computes true **word-level** `start_ts`/`end_ts` in `join_timestamps`; that path needs torch and I did not run it.)

**Getting *words* out of phonemes works, and is imperfect in a benign way.** Both models emit a literal `' '` phoneme between words, so word spans fall out by splitting on it. Over 106 words of textbook prose I measured **102 groups — a 3.8% deficit, 3 of 8 sentences affected**. The cause is systematic: espeak-ng cliticises unstressed function words, so "on the" comes back as one group `ɔnðə`. The cursor would occasionally be two words wide, roughly once per 25 words. It would never be *wrong* — the highlighted span always genuinely contains what is being spoken. Set that against [[04]] §6's rejected estimator, which after one chunk was 20-30 words adrift and "actively misleading"; this is a different and far more acceptable class of imprecision. Two hazards I did **not** quantify: espeak expands "55" → "fifty five", which *adds* groups and cuts the opposite way from the merges, and my corpus deliberately avoided numbers — textbooks are full of them. So mapping groups onto [[02]]'s text-layer offsets must be a sequence **alignment**, not a zip of two equal-length lists.

**On speed, Piper and Kokoro are not in the same category.** Piper: **RTF 0.045 — 22x real time**, ~200-350 ms to synthesise a whole sentence, cold start 1.04 s paid once at app launch. Kokoro on the same sentences, after thread tuning worth ~25%: **RTF ~0.41, 2.4x real time, 1.8-2.4 s per sentence**. Both stay ahead of playback indefinitely and both pipeline the way [[04]] keeps two utterances in flight — the difference is entirely the *first* sentence. Kokoro costs ~2 s of dead air on pressing play (hideable by synthesising sentence one during page render, not on the click); Piper's press-play latency is ~200 ms. Piper does not stream sub-sentence — the first chunk it yields is the whole sentence — so the unit of scheduling stays the sentence, exactly the shape `prototype-05` already has. While one 5 s sentence plays, Piper can synthesise ~110 s of audio.

**The timing seam does come back, and it is smaller and safer than either [[04]] designed or [[10]] feared.** `speechSynthesis.speak()` becomes an `AudioBuffer` on an `AudioBufferSourceNode`. Sentence advance is still an *event*, not an estimate — `onended` maps one-to-one onto `speakOne()`'s `u.onend` at `main.js:487` — so [[10]]'s one-sentence-per-unit invariant is untouched. Word position becomes `requestAnimationFrame` reading `audioCtx.currentTime` and binary-searching a **span table computed before the first sample plays**. The distinction that matters: [[04]]'s seam was an abstraction over an *unsolved estimation problem* with three implementations because nobody knew which would drift. Here there is no estimation — it is a lookup table. So the word cursor **reopens**, the seam **returns** in this much thinner form, and estimated cadence, the drift model, the re-seeding, the 1400 ms watchdog, the voice-picker capability labelling and the `localService` predictor all **stay cancelled permanently** — not merely unnecessary now, but inapplicable. Two genuinely new problems replace them: the app owns the buffer queue (so `pump()` becomes "keep N seconds ahead", needing a memory bound — don't buffer the page), and rate change inverts from [[04]] §5.3's expensive `cancel()`+re-dispatch to a free `playbackRate` tweak that rescales every span (and Piper has a native length-scale that changes speed without pitch-shifting — a deliberate choice, not the same thing).

**The two facts that argue against, and they are real.** First, **form factor**: today this is a **local app with a Python sidecar**, not a thing that runs in a tab. That is what I ran, and for a prototype already served over `http://localhost` it is a small piece of work. Kokoro has the only documented tab-shaped story (`kokoro-js`/Transformers.js, WASM or WebGPU, q8 ~92 MB) — but it is the *slow* model, and **I did not measure browser RTF**, which is the single number deciding whether that story is real. Piper has the numbers and **no verified browser path**: the blocker is espeak-ng, a C library needing its own WASM build. Second, **licensing, where the popular summary is stale**: Piper is **GPL-3.0**, not MIT. MIT `rhasspy/piper` was archived read-only in October 2025; the maintained `piper1-gpl` is GPL because it links espeak-ng. 2026 write-ups still listing "Piper (MIT)" are a year out of date. Piper voice models are also licensed **individually** — `en_US-lessac-medium` inherits CSTR Edinburgh's Blizzard 2013 research licence — so per-voice review is mandatory. Kokoro's weights are cleanly Apache-2.0, but `kokoro-onnx` pulls `phonemizer`+espeak-ng, so GPL re-enters through the phonemiser anyway; only the JS route realises the Apache promise. Shipping weight: Piper ~97 MB (runtime + one medium voice, 63 MB *per additional voice*); Kokoro fp16-timestamped ~191 MB but **all 54 voices in one 28 MB file**.

**On voice quality I have no ears and did not pretend to.** I synthesised the same textbook paragraph through both and left four files at `/tmp/claude-1000/tts/samples/` — `piper_lessac_medium.wav`, `kokoro_af_heart.wav`, `kokoro_bf_emma.wav`, `kokoro_am_michael.wav`. **Listen to those before acting on any of this**: if Piper is listenable the decision is easy, because everything else about Piper is better; if it is not, it becomes a real trade between 2 s of press-play delay and a good voice. On the rest of the field — **"omnitts" does not appear to exist under that name**; the nearest real things are **OuteTTS** (closest phonetic match) or the **Qwen-Omni** family, and both are autoregressive, which is disqualifying for this ticket's purpose. **XTTS-v2** is CPML non-commercial with nobody left at Coqui to sell a licence; **F5-TTS** is MIT code but CC-BY-NC *weights*; **Chatterbox** is genuinely MIT but GPU-shaped; **Orpheus** is 3B params and ~8 GB VRAM, out of scope on this machine; **MeloTTS** I did not get to (gap). The pattern worth keeping: **alignment comes free only from non-autoregressive duration-predictor architectures** — VITS (Piper) and StyleTTS2 (Kokoro). Every LLM-based TTS generates audio tokens without ever computing a phoneme duration, so word timing there needs a separate forced-alignment pass. The architectures that are fastest on CPU and the ones that hand you timings are the same architectures — which points hard at exactly the two candidates that were worth measuring.

Not established, so it is not mistaken for settled: browser RTF for Kokoro under WASM/WebGPU; whether Piper can run in a browser at all; voice quality; text-normalisation effects on word mapping; MeloTTS; and long-run behaviour (I synthesised sentences, not a chapter — memory growth and sustained-load RTF are untested).
